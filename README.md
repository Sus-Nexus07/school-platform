# 🎓 EduFlow

A full-stack school learning platform built from scratch — think Google Classroom, but built line-by-line to actually understand how every piece works.

**Live app:** https://school-platform-production-62be.up.railway.app

---

## What EduFlow Does

EduFlow lets teachers create courses, publish lessons, post assignments, and grade student work — while students enroll in courses, read lessons, and submit assignments. Admins get a control panel to oversee the whole platform.

Three roles, three experiences:

- **Students** — enroll in courses, read lessons, submit assignments, see their grades
- **Teachers** — create courses, publish lessons, post assignments, grade submissions
- **Admins** — view all users, view platform-wide stats, manage user roles

## Tech Stack

| Layer | Technology | Why |
|---|---|---|
| Backend | Go (`net/http`, no framework) | Fast, typed, and forces you to understand HTTP instead of hiding it |
| Database | PostgreSQL | Real relational data — users, courses, and enrollments all reference each other |
| Frontend | Vanilla HTML, CSS, JavaScript | No framework — every DOM update and fetch call is understood, not abstracted away |
| Auth | JWT (JSON Web Tokens) | Stateless sessions — no server-side session storage needed |
| Deployment | Railway | Free tier, auto-deploys from GitHub on every push |

## Architecture

```
school-platform/
├── main.go              # Entry point — loads config, connects DB, starts server
├── db/
│   └── db.go             # PostgreSQL connection
├── models/                # Data shapes (User, Course, Lesson, Assignment, Submission, PasswordReset)
├── handlers/               # Business logic for every API route
├── middleware/              # JWT auth verification ("the bouncer")
├── routes/                   # URL → handler mapping
├── utils/                     # Shared types (JWT claims, context keys)
├── static/                     # Frontend — HTML/CSS/JS served directly by Go
└── schema.sql                  # Database table definitions
```

**Why no frontend framework?** The goal was to deeply understand `fetch`, the DOM, and how a browser actually talks to a backend — not to hide that behind React abstractions on a first full-stack project.

**Why no backend framework (no Gin, no Echo)?** Same reasoning — using Go's built-in `net/http` means every route, every middleware wrapper, and every JSON encode/decode was written and understood personally, not generated by a framework.

## Database Schema

Seven tables, all relationally connected:

| Table | Purpose |
|---|---|
| `users` | Every person on the platform — students, teachers, admins |
| `courses` | Classrooms created by teachers |
| `enrollments` | Many-to-many join table linking students to courses |
| `lessons` | Content published inside a course, ordered by `position` |
| `assignments` | Tasks teachers post with a due date |
| `submissions` | Student work, with a nullable `grade` until graded |
| `password_resets` | One-time, time-limited tokens for password recovery |

**Key design decision — the `enrollments` table:** Rather than storing a list of student names inside each course, enrollments live in their own table linking `user_id` and `course_id`. This is a classic many-to-many relationship — a pattern that shows up in almost every real-world backend.

**Cascading deletes:** Every child table (`lessons`, `assignments`, `enrollments`, `submissions`) uses `ON DELETE CASCADE` on its foreign keys. Deleting a course automatically cleans up everything connected to it — no orphaned data, no manual cleanup queries needed.

## Authentication & Security

- **Passwords** are hashed with `bcrypt` before ever touching the database — plaintext passwords are never stored
- **JWT tokens** carry the user's ID and role, signed with a server-side secret, expiring after 24 hours
- **Middleware ("the bouncer")** verifies every protected route's token before the request reaches any handler
- **Role-based access control** — handlers check `claims.Role` to ensure students can't create courses, and teachers can't touch another teacher's course
- **Password resets** use cryptographically random tokens (`crypto/rand`, not `math/rand`), expire after 15 minutes, and are single-use — even if someone intercepts an old reset link, it's already dead
- **Parameterized SQL queries** throughout — no string concatenation into SQL, which blocks SQL injection entirely
- **`.env` / secrets** are never committed to GitHub (`.gitignore` from day one) — production secrets live only in Railway's environment variables

## Running Locally

```bash
# 1. Clone the repo
git clone https://github.com/Sus-Nexus07/school-platform.git
cd school-platform

# 2. Set up PostgreSQL and create a database
sudo -u postgres psql
CREATE DATABASE school_platform;
CREATE USER school_user WITH PASSWORD 'yourpassword';
GRANT ALL PRIVILEGES ON DATABASE school_platform TO school_user;
\q

# 3. Apply the schema
psql -U school_user -d school_platform -f schema.sql

# 4. Create a .env file
PORT=8080
DB_URL=postgres://school_user:yourpassword@localhost:5432/school_platform?sslmode=disable
JWT_SECRET=your-secret-key

# 5. Install dependencies and run
go mod tidy
go run main.go
```

Visit `http://localhost:8080` in your browser.
